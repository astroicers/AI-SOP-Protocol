# [ADR-034]: gate pseudocode 四層標記——把「能跑 / 靠判斷 / 欠實作 / 只是意圖」分開寫

| 欄位 | 內容 |
|------|------|
| **狀態** | `Draft` |
| **日期** | 2026-08-18 |
| **決策者** | ASP framework maintainers |
| **觸發事件** | 三次「不知情執行者」實測(#101 的 G5、#105 的 G2/G4)共報回 **23 個 pseudocode 缺陷,逐條查證後全部屬實**。根因是 `pipeline.md` 用 `FUNCTION`/`IF`/`RETURN` 的形式包裝**四種性質完全不同的東西**,而形式讓它們看起來一樣——執行者因此期待精確,並把「沒實作」與「本來就要靠判斷」一律回報為缺陷 |
| **關聯** | ADR-015(偽代碼三分法,本 ADR 把它套到唯一沒被處理的大檔);ADR-020(語意型義務不強行 hook,列為誠實殘留);ADR-022(POC 證實語意檢查無法便宜機械化 → 降級 advisory 的先例);ADR-023(純散文 + 無機械門檻 = 治理劇場);ADR-033(#101,本系列實測方法的起點) |

> **狀態說明:** `Draft`(初稿,禁止實作生產碼)→ `FIRM`(允許實作 POC/commit,需 Verification Evidence,audit 輸出 🟡)→ `Accepted`(人類看驗證結果後審核直升)。
>
> **本 ADR 以 Draft 起始**:它改變六道 gate 的書寫方式,是治理框架核心文件的形式變更,
> 不該由任何一個功能 PR 夾帶。實作須待人類裁決。

---

## 背景(Context)

### `pipeline.md` 是唯一沒被 ADR-015 處理過的大型 pseudocode 檔

ADR-015(Accepted,2026-06-11)已經為「LLM 被要求在腦中執行偽代碼」定調:

> 這些都是**可確定性判斷的邏輯**,由 LLM 當直譯器執行**既不可靠**(每次「執行」結果可能不同)**也昂貴**(1,587 行 context 稅)。

它提出**三分法:下沉腳本 / 保留語意 / 刪除重複**,把 `task_orchestrator.md` 從 1,587 行砍到約 300 行。

但 ADR-015 **只處理了那一個檔**。`pipeline.md` 在其中僅以「外部錨點,不可斷裂」的身分出現(L33、L106),從未被同樣處理。而它今天是 595 行、六道 gate、約 400 行 gate 本體,**全 repo 零實作**——六道 gate 中唯一指向真實可執行檔的只有 ADR-033 加的 `lint_skill.py`。

三分法**沒有被宣告為通則**,後續也沒有 ADR 一般化它。因此套到 `pipeline.md` 是**新決策**。

### 實測資料:23 個缺陷,約一半是形式造成的

方法沿用 ADR-033:派**不知情執行者**——只給 `pipeline.md` 與 artifacts,不提任何 skill、不提任何 ADR、禁讀 `docs/adr/`。情境做成最正常的樣子,不針對已知缺陷調校。

| gate | pseudocode 缺陷 | 額外實質發現 |
|---|---|---|
| G5(#101) | 6 | — |
| G2(#105) | 8 | 2 |
| G4(#105) | 9 | 3 |

**三位執行者都逐行追、算 state、回報哪些分支觸發、哪些跳過。** 它們把它當程式讀,
因為它長得像程式。而其中大量「缺陷」的內容是:某個函式沒有定義來源、某個判斷在此情境下
無法決定真假、某個宣告與前面的邏輯對不上。

**那些只有在期待精確執行時才是缺陷。**

### 量測:六道 gate 的檢查實際上是什麼組成

> ⚠️ **本節更正了本 ADR 初稿的框架。** 初稿寫「約一半的缺陷是形式造成的幻覺」,
> 逐條量測後**那個比例不準**——大部分不是「語意上做不到」,是「可機械化但沒人寫」。
> 那兩者的處置完全不同,把後者標成「執行者裁量」會是第二次說謊。
> 量測在人類裁決前完成,所以還來得及改。

`EXECUTE()` 的六個目標**全部指向真實存在的東西**(ASP 自己 `test` / `lint` /
`test-filter` / `audit-quick` 都有);但 pseudocode 呼叫的**八個判斷 helper,零實作**。
逐個分類後:

| 層 | 數量 | 實例 | 補救方式 |
|---|---|---|---|
| **能跑**(mechanical) | 6 | `make test` / `make lint` / `make test-filter` / `make audit-quick` / grep / `lint_skill.py` | 無須補救 |
| **靠判斷**(judgment) | ~7 | `is_binary_testable`、`has_test_for`、`pre_commit_checklist`、`qa_agent.independent_verify`、`sec_agent.review`、skill craft、G2 三旗標的資料來源 | **不預期會機械化**;標示即誠實 |
| **欠實作**(debt) | **5** | `count_assertions`、`git_diff_files`、`matches_scope`、`test_checksums_changed`、`has_cycle` | **可機械化,而且很便宜** |
| **只是意圖**(intent) | 16 | `quality-thresholds.yaml` 中從未被任何 pseudocode 讀取的 threshold 鍵 | 要嘛接上、要嘛刪 |

**「欠實作」那五個是本次量測最有價值的產出。** 它們不是語意難題:
`count_assertions` 的註解裡連 regex 都寫好了(Go/Python/TS 各一組)、
`git_diff_files` 是一行 git、`matches_scope` 是 glob 比對、
`test_checksums_changed` 是 sha256 比對、`has_cycle` 是圖環偵測。

**五個小 shell 函式,估計 150 行左右——那不是 ADR-015 選項 B 的「SPEC 等級以週計」,是一個下午。**
在量測之前無法知道這件事,因為它們混在 23 條缺陷回報裡看起來跟語意問題一樣。

## 評估選項(Options Considered)

### 選項 A:三層標記(採用)

在每個檢查點標出它屬於哪一層,**不動語法、不動判定邏輯**。

- **優點**:成本是一次標記 pass;**零行為變更**;直接消除約一半的實測缺陷;與 ADR-022 的
  advisory 降級先例同構(該 ADR 的 POC 證實語意檢查無法便宜機械化後,誠實降級並記錄)
- **缺點**:`pipeline.md` 仍是散文,ADR-023 警告的「治理劇場」風險不會消失,只是不再假裝
- **風險**:標記本身也是散文,同樣會被壓縮蒸發(ADR-020 的病)。緩解:標記寫在**每個檢查點旁**
  而非集中在檔頭,壓縮時與被標記的內容同進退

### 選項 B:照 ADR-015 三分法下沉腳本

把 G1–G6 的確定性部分實作成 `.asp/scripts/gates/*.sh`。

- **優點**:確定性部分真的變 exit-code 級可判、可測試、可 diff——ADR-022 對機械軸的期待
- **缺點**:SPEC 等級工程,以週計。而 `.asp-gate-log/` 分布是
  **G1×18 / G2×10 / G3×2 / G4×2 / G5×0 / G6×0**、最近一筆 2026-07-29——
  **為走過兩次的門蓋鋼筋,投資報酬極低**
- **風險**:ADR-022 的 POC 已證實語意部分無法便宜機械化。下沉只能處理一小部分
  (`git_diff_files` / `matches_scope` / `{ext}` 之類),而那正好是本 ADR 建議另立 SPEC 的子集

### 選項 C:什麼都不做

- **優點**:零成本
- **缺點**:形式繼續邀請精確執行。**已實測會發生**:三次探測、每次都報同一族缺陷
- **風險**:每個新執行者都會再付一次這個學費,而且會把「未定義」誤讀為「缺陷」寫進報告

## 決策(Decision)

**選擇選項 A**,附四個設計決定。

### D1. 四層的判準

| 標記 | 判準 | 補救方式 | 寫法 |
|---|---|---|---|
| `mechanical` | 有真實可執行檔/指令,**今天就能跑** | 無須 | 指向實際路徑;**不得指向不存在的東西** |
| `judgment` | 需要語意理解,**且不預期會機械化** | 無(這是它的本質) | 明示「無機械判準,執行者裁量」+ **判斷時該看什麼** |
| `debt` | 被 pseudocode 呼叫、**零實作**,但**可機械化** | 寫那個函式 | 明示「未實作」+ **預估難度** |
| `intent` | config 定義了但**沒有任何一步讀它** | 接上或刪除 | 明示「非生效門檻」 |

**`debt` 與 `intent` 為什麼要分開**(初稿把它們合併,是錯的):
- `debt` 是**被呼叫但沒實作**(`count_assertions` 有呼叫點,回傳值直接決定 issue)
- `intent` 是**定義了但沒被呼叫**(`max_open_questions` 沒有任何一行讀它)

補救方式完全不同:前者要寫函式,後者要決定接上還是刪掉。合併會讓那份 150 行的欠債清單
消失在「意圖」裡——而它正是本次量測最有價值的產出。

**`judgment` 與 `debt` 的邊界**:判準是「**是否預期它會機械化**」,不是「現在有沒有實作」。
`is_binary_testable` 判散文條件能否二元測試——那是語意的,標 `judgment`;
`count_assertions` 數 assertion——註解裡連 regex 都給了,標 `debt`。
**有疑義時歸 `debt`**:ADR-022 的教訓是「可機械化」與「已機械化」之間常常就是整個 POC,
標 `debt` 會逼出那個評估;標 `judgment` 則會讓它永久沉沒。

### D2. 不改語法,只加標記

`FUNCTION` / `IF` / `RETURN` 保留。理由:

1. ADR-015 特別保護了 `pipeline.md` 的外部錨點(`asp-dispatch`/`asp-impact`/`asp-autopilot`
   都引用其內部符號),改語法會斷鏈
2. 語法本身不是問題,**沒有標示哪些是裁量點**才是問題
3. 改語法是不可逆的大改;加標記可逆

### D3. 16 個未讀 threshold 鍵:標為意圖紀錄,**不刪**

實測 `quality-thresholds.yaml` 共 19 個 threshold 鍵,`evaluate_G*` 真正取用的只有
G2 的 `min_acceptance_criteria` 與 `G5_integration` 整段(ADR-033 後續 PR 接的)。

刪除會丟失「某人曾經認為這該被檢查」這個資訊,而那正是未來要機械化時的需求清單。
標為意圖紀錄同時達成誠實與保留。(#106 已在該檔與快速參考表加了聲明,本 ADR 追認並系統化。)

### D4. 確定性子集另立 SPEC,**不夾帶進標記 pass**

`git_diff_files()` / `matches_scope()` / `{ext}` 是 ADR-015 第 1 類(可下沉)。
把它們的實作夾帶進一個「形式標記」的變更,會重蹈 ADR-033 自己記錄的錯誤:
「不該由一個功能 PR 夾帶改動治理框架的核心術語定義」。

### D5. 收窄 `pipeline.md:615` 的量化摘要要求

L615 目前寫:

> Gate 評分必須對照具體數字,不得使用「基本達標」等主觀描述。

L617 進一步要求**必須輸出**一張四欄量化摘要表。**這與本 ADR 直接衝突**——
一個標為 `judgment` 的檢查,在「實際值」欄要填什麼?

實測顯示這不是理論衝突:G2 的執行者產出 13 列摘要表,裡面混著可數的
(「SPEC 欄位數 = 7」)與它自己判的(「Done When 可二元測試 = 4/4」);
G4 的執行者則在表裡填了四個 `⏭ 不適用`。**同一條規則,兩個執行者兩種應對。**

收窄為:

> Gate 評分**在 `mechanical` 檢查上**必須對照具體數字,不得用主觀描述。
> `judgment` 檢查不填「實際值」,填**判斷 + 依據**,狀態標 `judgment`。
> `debt` 與 `intent` 檢查**照列但標明未生效**,不得以空白或 `N/A` 混過。

**保留 L615 的原意**(禁止「基本達標」這種空話——裁量也要寫依據),
**只否定它「一切皆可量化」的隱含前提**。

**副產物**:摘要表底部自然得出一道 gate 的 `mechanical / judgment / debt / intent` 分布
——**那個比例就是這道 gate 有多硬的量測**,而目前完全看不到。
依本 ADR 的量測,G4 大致是 2 / 2 / 3 / 4。

## 後果(Consequences)

**正面影響:**
- 執行者不再把裁量點誤讀為缺陷——實測顯示這佔回報量的約一半
- gate evidence 的可信度提升:讀者能分辨「機械驗過」與「某人判斷過」
- 未來要機械化時,意圖紀錄就是現成的需求清單

**負面影響 / 技術債:**
- **`pipeline.md` 仍然是散文治理層**。本 ADR 讓它誠實,不讓它變強制。
  ADR-023 的「治理劇場」風險依然存在,只是不再自我欺瞞
- 標記會增加行數。ADR-022 複雜度棘輪:目前 `profiles.total_lines` 3790,baseline 5177,
  預估標記 pass 增加 100–150 行,仍有餘裕;**若逼近 baseline 須停下重新評估**
- 標記本身可能被壓縮蒸發(ADR-020 的已知病)。D1 要求標記寫在檢查點旁而非檔頭,緩解但不根治

**後續追蹤:**
- [ ] 標記 pass 完成後,**再派一次不知情執行者**跑同一道 gate,量測缺陷回報數是否下降
      ——這是本 ADR 唯一的可驗證成功指標
- [ ] **`debt` 五項的機械化**(`count_assertions` / `git_diff_files` / `matches_scope` /
      `test_checksums_changed` / `has_cycle`,估 ~150 行 shell)——D4 的 SPEC 就是這份清單,
      **範圍比本 ADR 初稿預估的小一個量級**
- [ ] G1 / G3 / G6 尚未探測;標記 pass 前後各跑一次可同時當對照

## 成功指標(Success Metrics)

| 指標 | 目標值 | 驗證方式 | 檢查時間 |
|------|--------|----------|----------|
| 裁量點誤報下降 | 同一道 gate 的「未定義/不清楚」類回報顯著減少 | 標記前後各派一次不知情執行者,比對第 4 項回報數 | 標記 pass 後 |
| 零行為變更 | 六道 gate 的 PASS/FAIL 結果與標記前完全相同 | 標記只加註解、不動條件式;逐 gate diff 檢查 | 標記 pass 當下 |
| 複雜度未觸發棘輪 | `profiles.total_lines` < 5177 | `make profile-validate` + 行數計算 | 標記 pass 當下 |
| 意圖紀錄不被誤讀 | 執行者不再把未讀 threshold 當成生效門檻 | 同上探測的回報內容 | 標記 pass 後 |
| **欠債清單可執行** | `debt` 標記能直接當 SPEC 的需求清單,無須再分析 | 標記 pass 後檢視該清單是否逐項可估工 | 標記 pass 後 |

**何時該重新評估**:若標記後執行者的誤報數**沒有下降**,代表診斷錯了——
問題不在形式而在別處,應回頭考慮選項 B。
